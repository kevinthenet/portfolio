# Portfolio site — project notes for Claude

Kevin Castro's personal portfolio: Astro 7 (static output), content
collections for projects/blog/recommendations, hand-rolled CSS design
system ("Uplink // Terminal" — terminal x cyberpunk, see `DESIGN-TODO.md`
for the design pass history and any open items).

## Package manager: pnpm, not npm

`package.json` pins `packageManager: pnpm@11.10.0`. **Always use `pnpm`**
for install/build/dev in this repo — mixing `npm` and `pnpm` against the
same `node_modules` has caused real problems here (see the `sharp` gotcha
below). `pnpm-workspace.yaml` at the root is just an `allowBuilds` allowlist
for postinstall scripts, not a multi-package workspace — don't assume
nested `package.json` files (e.g. `tools/og-cards/`) are pnpm workspace
members; they're deliberately isolated with their own installs.

## Image pipeline (astro:assets)

Project/recommendation photos live in `src/assets/` (NOT `public/`) and are
referenced from content-collection frontmatter via relative `image` paths,
e.g. `image: '../../assets/projects/<slug>/foo.png'`. The
`photos`/`profileImage`/`heroImage` schemas in `src/content.config.ts` use
the `image()` helper so Astro optimizes/resizes them at build time and
`Slideshow.astro`/`Card.astro` render them with `<Image />`.

**`sharp` must be an explicit devDependency**, not just present
transitively. pnpm's strict `node_modules` won't hoist/symlink a package
that isn't directly declared, even if some other dependency (astro, vite)
pulls it in transitively — the optimized-image service will silently do
nothing and `astro build` will warn `MissingSharp` for every image. If you
ever see that warning, check `sharp` is still in `package.json`
devDependencies before debugging anything else.

Animated GIFs cannot go through `<Image />` — Sharp flattens them to a
single frame. If you ever need to add motion back to a project (there's
currently none; the last GIFs on the site were removed for exactly this
reason), use a muted looping `<video>` instead, not `<Image>`.

Assets that need a **stable, unhashed absolute URL** — favicons,
`site.webmanifest`, `robots.txt`, and OG/share-card images (see below) —
stay in `public/`, not `src/assets/`. That's a deliberate split, not an
oversight.

## OG/share cards

Every project page and (once posts exist) every blog post gets its own
1200x630 OG/Twitter share card, generated by a standalone tool at
`tools/og-cards/` — **read `tools/og-cards/README.md` before touching
anything OG-card related**. Key points:

- It's a separate Node project (own `package.json`/`node_modules`,
  Playwright + sharp + gray-matter) so it never touches the site's
  dependency graph. Astro doesn't process it.
- Card copy is read live from content-collection frontmatter, not
  duplicated — rerun `node generate.mjs` after changing a project's
  `subtitle`/`tag`/`date`/`blurb` or a post's `title`/`summary`/`tags`.
- `src/utils/og-image.ts`'s `resolveOgImage()` checks the generated file
  actually exists and falls back to the site-wide `public/og-image.png`
  if not — so a newly-added project/post won't have a broken `og:image`
  until someone runs the generator, but it also won't error the build.
  Don't forget to actually run it when adding content.

## Content collections

`src/content.config.ts` defines `blog`, `projects`, `recommendations`. All
three currently have real content except `blog`, which is empty — expect
`[WARN] [glob-loader] No files found matching "**/*.md" in directory
"src/content/blog"` on every build/check; that's expected, not a bug.

## `.astro/` generated types

`.astro/types.d.ts` (gitignored) gives `getCollection()`/`CollectionEntry`
their real types instead of `any`. It's regenerated by `astro dev`,
`astro build`, `astro sync`, or `astro check`. **Don't `rm -rf .astro` and
leave it deleted** — if you clean it up mid-session, regenerate it
afterward (`npx astro sync`) so the editor's TS server doesn't report
false implicit-any errors on `getCollection` callbacks in
`src/pages/**/*.astro`.

## Cypress

- `cypress/tsconfig.json` is a standalone TS config (target `ESNext`,
  `moduleResolution: "Bundler"`, `skipLibCheck: true`) — it intentionally
  does **not** reference `.astro/types.d.ts`; no spec needs
  `astro:content` types (`cypress/constants.ts` hardcodes content
  directory strings specifically to avoid that dependency).
- No script in `package.json` actually runs `tsc -p cypress/tsconfig.json`
  — it exists for editor/IDE type-checking only.
- Cypress's Electron runner can fail to launch in sandboxed/headless shells
  with `bad option: --no-sandbox` — that's an environment limitation of
  whatever shell you're in, not a repo bug. Verify with `tsc --noEmit -p
cypress/tsconfig.json` + `astro check` when you can't actually launch
  the browser runner.

## Root tsconfig

`tsconfig.json` extends `astro/tsconfigs/strictest`, which includes
`exactOptionalPropertyTypes: true`. This means an optional prop typed
`foo?: string` cannot be assigned an explicit `string | undefined` value —
if you thread an optional prop through multiple layout layers (see
`image?` in `Head.astro` → `Base.astro` → `ProjectHighlight.astro`/
`Blog.astro`), either give every layer a concrete default value, or type
the prop as `foo?: string | undefined` explicitly at the layer that
receives a possibly-undefined value.

## Before committing

`pnpm run build`, `npx astro check`, and `pnpm run lint:check` (prettier)
should all be clean. Clean up `dist/` and `.astro/` if you generated them
mid-session and don't need them for the editor afterward — but see the
`.astro/` note above about regenerating types before finishing up. Prefer
several small, logically-scoped commits over one large one.
